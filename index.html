System Design Interview — 1-Page Cheat Sheet

TL;DR Clarify → Estimate → API & data → Draw → Deep-dive → Wrap up. Think out loud. Every choice gets a “because…” and a “the trade-off is…”

They grade scoping · a design that works · depth on 1–2 hard parts · trade-offs · communication

9Sharding & replication

Sharding = split data across machines

Strategy+−
Hash of keyEven spreadResharding moves data → use consistent hashing
Range (date, A–M)Fast range scansHot spots (e.g., today's data)
Lookup tableFlexibleExtra service to depend on
GeographyData near users, legal rulesUneven load

Good shard key: many distinct values, spreads evenly, matches your main query (user_id, chat_id). Cross-shard joins hurt.

Consistent hashing: servers + keys on a ring (with virtual nodes); adding a server moves only ~1/N of the keys.

Replication = keep copies

Type+−
Leader → followersSimple, scales readsReplica lag; needs failover
Multi-leaderWrites in many regionsWrite conflicts
Leaderless (quorum)Survives node failuresConflict resolution

Quorum: N copies, write to W, read from R. R + W > N → reads see the latest write. Read-your-own-writes: send a user's reads to the leader right after they write.

10Consistency & CAP

CAP: when the network splits, choose — answer correctly or not at all (C), or always answer, maybe stale (A).

Pick Consistency (CP)
  • Payments, bank balances
  • Inventory, seat booking
  • Leader election, locks
Spanner, etcd, ZooKeeper, SQL primary
Pick Availability (AP)
  • Likes, views, follower counts
  • Feeds, timelines
  • Shopping cart, presence
Cassandra, DynamoDB (default)

PACELC: even with no split, you trade latency vs consistency.

Levels (strong → weak)

Strong→ Read-your-writes→ Causal→ Eventual

Transactions

One DB → ACID transaction. Across services → Saga (steps + undo steps). Avoid two-phase commit unless forced.

Say: “Like counts can be eventually consistent; payments must be strongly consistent.”

12Reliability patterns

PatternIn plain words
TimeoutsNever wait forever
Retries + backoff + jitterRetry blips, spread out so you don't stampede
Idempotency keyDoing it twice = doing it once (payments!)
Circuit breakerStop calling a service that keeps failing
Dead-letter queuePark messages that keep failing, inspect later
BulkheadsSeparate pools so one failure doesn't sink everything
Graceful degradationServe less (hide recommendations) instead of erroring
Outbox patternSave DB row + event in one transaction, publish after

Delivery: at-most-once · at-least-once (+ idempotent consumer ≈ exactly-once) · true exactly-once is hard.

Disaster recovery: RPO = how much data you can lose · RTO = how long until you're back.

13Rate limiting & unique IDs

Rate-limit algorithmNote
Token bucket ⭐Allows short bursts; most common
Leaky bucketSmooth, constant output rate
Fixed windowSimple; up to 2× burst at window edges
Sliding window logExact; memory-heavy
Sliding window counterGood balance of both

Counters in Redis (atomic INCR + EXPIRE, or a Lua script), keyed by user / IP / API key → reply 429 + Retry-After.

ID option+−
DB auto-incrementSimple, orderedOne bottleneck; guessable
UUID v4No coordinationRandom → slow indexes
Snowflake (64-bit)Sorted by time, distributedClock skew
UUID v7 / ULIDTime-sortable UUID128-bit

Snowflake = 41 bits time (ms) + 10 bits machine + 12 bits sequence (~4K IDs/ms per machine). Base62 × 7 chars ≈ 3.5 trillion short codes.

16Do / Don't

✅ Do
  • Ask questions before drawing
  • Say numbers & assumptions out loud
  • Start simple, then scale it
  • Name the bottleneck & single point of failure yourself
  • Give a trade-off for every choice
  • Mention monitoring & security (auth, encryption)
  • Ask: “Which part should I go deeper on?”
❌ Don't
  • Jump into boxes before requirements
  • Name-drop tech without “because…”
  • Over-engineer (Kafka + 20 microservices for 1K users)
  • Go silent — think out loud
  • Spend >10 min on requirements & math
  • Defend a bad choice after a hint — adjust
Stuck? Go back to the numbers → find the bottleneck → grab a fix from card 7.
